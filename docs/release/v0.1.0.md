# Release v0.1.0 — 2026-10-31

## Qué trae

Primera versión publicada del canal WhatsApp bancario: todo el recorrido de una conversación, desde que el mensaje
llega por WhatsApp hasta que el agente responde, con los servicios bancarios detrás.

- **Servicios bancarios** (`services/`): usuarios (H1), acceso y sesión (H2), canal y vínculo de WhatsApp (H3),
  cuentas y transferencias (H4), tarjetas (H5) y seguros (H6).
- **Plataforma** (`platform/`): eventos Kafka (H0.1) y orquestador de conversaciones (H0.2).
- **Gateway** (`gateway/`): WhatsApp sobre Twilio (H0), con validación de firma y ACK rápido.
- **IA** (`ai/`): capa MCP (H7), base de conocimiento RAG (H8) y agente conversacional (H9).

## Incluye

Los 14 PRs abiertos forman una cadena lineal (cada rama salió de la anterior) y todo su contenido está en la rama de
esta release; se cierran al lanzar la versión.

- #2 — Servicio de Usuarios bancarios (H1): alta, consulta, actualización y cambio de estado, con auditoría.
- #3 — Servicio Canal WhatsApp (H3): términos, verificación de identidad, vínculo y re-vínculo, perfil y preferencias.
- #4 — Acceso y Sesión (H2): emisión, validación, renovación y revocación de credenciales.
- #6 — Cuentas (H4): saldos, movimientos, terceros y transferencias con límites.
- #7 — Seguros (H6): pólizas, coberturas y reclamos.
- #8 — Plataforma de Eventos Kafka (H0.1): contratos versionados, reintentos, DLQ y trazabilidad.
- #9 — Gateway WhatsApp/Twilio (H0): webhook seguro, estados de entrega y envío de mensajes.
- #10 — Orquestador del Canal (H0.2): conversación, sagas, deduplicación y outbox idempotente.
- #11 — Tarjetas (H5): tarjetas, consumos, bloqueos y aviso de viaje.
- #12 — Capa MCP (H7): catálogo de capacidades de H1–H6 para el agente, con enmascarado de PII.
- #13 — Base de conocimiento RAG (H8): ingesta aprobada, versionado y búsqueda híbrida con citas.
- #14 — Agente conversacional (H9): Google ADK, guardrails, memoria de sesión e idempotencia.
- #15 — Arreglos de revisión de #2, #3 y #4 (auditoría de altas rechazadas, `Location` en el 201, token validado en
  el vínculo, autenticación de llamadas en acceso y sesión).
- #16 — Arreglo de revisión de #9: límite de body antes del buffering en los webhooks de Twilio.

## Requisitos de despliegue

- **Java 21** y el Maven Wrapper incluido (`./mvnw`) para los módulos Spring Boot: los seis servicios, los dos
  componentes de `platform/` y el gateway.
- **PostgreSQL**: una base por servicio (usuarios, acceso, canal, cuentas, tarjetas, seguros), una para el orquestador
  y una para la base de conocimiento con la extensión **pgvector** (imagen `pgvector/pgvector:pg17`).
- **Kafka** (modo KRaft; `apache/kafka:3.9.1` en los compose de desarrollo) con los topics de eventos recibidos,
  listos para enviar, estado y DLQ.
- **Redis** y el `agent-memory-server` para la memoria de sesión del agente (TTL de 30 minutos por defecto).
- **Python 3.12** con `uv` para los tres componentes de `ai/` (los tres `pyproject.toml` declaran `0.1.0`).
- **Variables de entorno**: cada módulo trae su `.env.example`. Las mínimas propias son la contraseña de base de datos
  (`DB_PASSWORD`, obligatoria para el chart de Helm de usuarios), `CREDENTIAL_JWT_SECRET` (32 bytes o más), los tokens
  de servicio entre componentes y, para el canal, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_WHATSAPP_FROM` y
  las URLs públicas del webhook y del status callback. Para el agente y la base de conocimiento, `GOOGLE_API_KEY`.
- **Puertos por defecto**: 8080 usuarios, 8081 canal, 8082 acceso y sesión, 8084 cuentas, 8085 seguros, 8086
  tarjetas, 8090 gateway, 8091 orquestador, 8092 plataforma de eventos, 8101 capa MCP, 8102 base de conocimiento,
  8103 agente.
- **Versiones de los módulos**: los `pom.xml` declaran `0.1.0-SNAPSHOT`; el equipo de release no cambia esa metadata.
  La versión publicada vive en la etiqueta `v0.1.0` y en este `CHANGELOG.md`.

## Cómo probarla

Con JDK 21, en cada módulo Maven (`services/<módulo>`, `platform/<componente>`, `gateway/wa-twilio-gateway`):

```
./mvnw -B clean verify
```

`wa-twilio-gateway` y `wa-channel-orchestrator` usan Testcontainers: sin Docker, agregar `-DskipITs`.

Para los componentes de IA, en cada `ai/<componente>`:

```
uv sync --frozen
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest -q -m "not evals"
```

Y en la raíz del repositorio:

```
python ai/verify.py
python -m unittest discover -s scripts -p "test_*.py"
helm lint services/wa-users-service/helm/wa-users-service
```

Las pruebas de evaluación del agente (`-m evals`) necesitan `GOOGLE_API_KEY` y no son parte de la verificación de la
release.

## Limitaciones conocidas

- El 201 de `POST /api/v1/tarjetas/{tarjetaId}/aviso-viaje` no devuelve identificador ni cabecera `Location` (hilo
  MEDIUM abierto del PR #11). El aviso de viaje se registra correctamente; sólo falta la referencia del recurso.
- Los hilos de revisión de #13 y #14 siguen abiertos en GitHub, pero sus hallazgos ya están corregidos en esta rama
  (identidad lógica `source_id` en H8 con migración `002_logical_source.sql`, `correlation_id` de la base de
  conocimiento tomado del turno, mensajes de límite sólo con evidencia de herramienta y timeout de turno de 4 s,
  menor que los 5 s de H0.2).
- El despliegue de usuarios descarta la implementación anterior que vivía en `main` (`com.bank.users`); la de esta
  release es `com.bcra.users.ws` y cubre alta, consulta, actualización, cambio de estado y auditoría.
